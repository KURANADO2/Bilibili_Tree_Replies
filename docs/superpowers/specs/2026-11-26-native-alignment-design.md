# 树形评论对齐原生体验设计文档

日期：2026-11-26
状态：待批准
来源：Chrome 商店用户反馈三条 + 维护者本人观察到的评论区闪烁问题

## 1. 意图与背景

用户反馈原文要点：

1. 默认情况下过多地显示回复，逻辑与原生评论区明显不同
2. 树形评论的单条高度明显高于原生，信息密度不如原生，两者叠加观感不好
3. 推荐添加显示 IP 属地功能

维护者（本项目所有者）对三条的定调：

1. 「默认展示回复」本身不改——这是插件的产品行为，反馈的第 1 条不采纳。但维护者自己观察到：打开视频后评论区持续闪烁一段时间才稳定，怀疑与加载方式有关，要求评估「是否一次性加载全部评论」，若是则改为按滚动加载更多
2. 密度优化：做，深度选「结构对齐原生」（AskUserQuestion 已确认）
3. IP 属地：评估结论为可实现，纳入本次改动

代码核查结论（本次会话逐行核对 content.js 与 styles.css 确认）：

1. 加载确实近似「一次性」：`loadRootComments`（content.js:388）自动连翻最多 `MAX_AUTO_ROOT_PAGES = 10` 页根评论（每页 20 条，上限 200 条），不等用户滚动；每页到达后 `autoLoadReplyPages`（content.js:565）把该页所有有回复的根评论入队，`runAutoReplyQueue`（content.js:574）逐个再发请求拉每棵回复树的第一页（最多又约 200 次请求、4000+ 条评论）
2. 闪烁的直接原因是渲染方式：`render()`（content.js:790）每次都 `list.innerHTML = state.roots.map(renderRoot).join("")` 全量销毁重建整个列表 DOM（content.js:818）。初始加载期间根评论翻页约 20 次全量重建 + 每棵回复树完成再触发 1 次（content.js:592），合计可达 200 多次；每次重建数千节点、头像图片全部重新加载，表现为持续闪烁，队列排空后稳定
3. 高度差实测于 CSS：单行文字的根评论约 163px = `.btr-root` 上下 padding 40（styles.css:111-114）+ 头像独占一行 38（styles.css:127-140）+ 正文 margin 8 + 行高约 25（styles.css:208-212）+ 元信息行 margin 8 + 约 18（styles.css:245-252）+「收起相关回复」按钮独占一行 margin 8 + 约 18（styles.css:335-340）。原生同类评论约 100px。四处结构差异：头像独占一行（原生头像在左与内容并排）、padding 偏大、元信息与操作入口分两行、长评论不按接口 `max_line` 折叠
4. IP 属地可实现：字段为 `reply_control.location`，值形如「IP属地：广东」；`normalizeReply`（content.js:195）已保留原始响应于 `raw` 字段（content.js:202），取用是一行代码。接口对登录请求才下发该字段，且仅 2022-07-25 之后发布的评论存在（公开 API 文档与多个开源项目的一致结论，实现时需登录态抽验）。插件请求优先走页面上下文、自带登录 cookie（content.js:369-386），登录用户可直接拿到

## 2. 目标、非目标、反目标

### 2.1 目标

1. 首屏接口请求从最坏 200+ 次降到约 20 次上下：根评论 1 页 + 该页每棵回复树第一页各 1 次；后续页随用户滚动加载
2. 初始加载与滚动加载期间不再闪烁：已渲染的评论 DOM 保持稳定，新数据以追加或单棵局部重建的方式进入
3. 单行根评论渲染高度逼近原生，目标约 100px（±20%），以浏览器实测对比同视频原生评论区为准
4. 登录状态下元信息行显示「IP属地：xx」；未登录、老评论静默不显示，无占位无报错
5. 保留树形缩进与层级线视觉表达（插件核心卖点）
6. 默认展示回复的产品行为不变：已加载到的根评论，其回复树第一页仍自动拉取并展开

### 2.2 非目标

1. 不做虚拟滚动——滚动分页 + 增量渲染后，DOM 规模增长与用户滚动深度成正比，可接受
2. 不做「默认收起 / 默认展开」设置项——维护者明确默认展示回复不改
3. 不为 IP 属地提供独立开关
4. 不做回复树内部的滚动无限加载，树内「加载更多回复」保持点击式
5. 不改动 API 请求通道结构（页面上下文优先、background 兜底的双通道不动，content.js:369-386）
6. 不引入 WBI 签名（现有通道已验证可用）

### 2.3 反目标（功能做出来也算失败）

1. 闪烁仍在：加载期间已渲染的评论仍被整列表销毁重建
2. 首屏请求数没有下降
3. 树形层级视觉（缩进线）丢失
4. 未登录用户因 `location` 字段缺失看到报错或空占位
5. 风控截断检测（`isRootListTruncated`，content.js:358）在首屏页数减少后误报或漏报
6. 发回复、点赞/点踩、排序切换、主题切换、切回原评论区、换视频（SPA 路由）等既有交互回归失败

## 3. 约束（代码事实与已知经验）

1. `render()` 是全量 `innerHTML` 重渲染，但 UI 状态不依赖 DOM 存活：展开/收起在 `store.expanded`（content.js:449）、回复输入框在 `state.activeReplyId`，均在 JS state 中；新增的长文折叠状态同样必须存 JS state
2. 根评论响应的 `replies` 数组自带 2～3 条预览回复，`seedPreviewReplies`（content.js:602）已实现零请求消费
3. `reply_control.max_line` 为接口下发的长文折叠行数（API 文档记载，根评论响应实测值为 6，实现时抽验）；缺失时按默认 6 处理
4. `isRootListTruncated` 只在接口声称 `is_end` 时被调用（content.js:424-428），比较 `all_count` 与已加载根评论的 `rcount` 总和；改为每次 1 页后该调用时机不变，少评论视频第一页即 `is_end`，检测语义保持
5. `runAutoReplyQueue` 已有代际保护（`storeGeneration`，content.js:583），排序切换/刷新/换视频时旧队列自动停止；增量渲染改造必须保留该机制
6. curl 高频直连接口会触发风控（返回 -352 或 HTML 错误页），验证一律走页面上下文或浏览器，不用裸 curl 下结论
7. 测试基建：`node --test test/`，现有 `test/theme.test.js` 为样例；纯逻辑模块参照 `src/theme.js` 的 UMD 模式（module.exports + 全局挂载）便于单测
8. 面板骨架（content.js:994-1016）：`.btr-list` 为列表容器，`.btr-footer` 内有「更多评论」按钮（data-action="load-roots"）；主题采样近期已修复为原评论区可见时跳过（commit e275ee0），本次不动 theme.js

## 4. 方案与取舍

### 4.1 加载策略：滚动分页

候选：

1. 保持自动连翻 10 页，仅优化渲染——不解决用户明确提出的「按需加载」诉求，请求量不变
2. 首屏 1 页 + 滚动触底自动加载下一页（选定）
3. 首屏 1 页 + 纯手动「更多评论」按钮——滚动体验倒退，原生就是滚动加载

选 2（维护者提出并确认）。具体语义：

1. `loadRootComments` 改为每次调用加载 1 页；`MAX_AUTO_ROOT_PAGES` 与 `ROOT_PAGE_INTERVAL_MS` 常量废弃
2. IntersectionObserver 观察 `.btr-footer`：可见、非忙（`loading`/`paging` 均 false）、未 `isEnd`、未 `truncated`、无 `error` 时触发加载下一页（error 态一并阻断自动触发，避免网络持续失败时的自动重试循环）
3. 「更多评论」按钮保留：兼作风控截断时的手动重试入口与无障碍兜底；截断态禁止 observer 自动触发，避免重试风暴
4. 回复树自动加载机制（`autoLoadReplyPages`/`runAutoReplyQueue`）保留，天然只为已滚动加载到的根评论排队；每棵树完成后的全量 `render()` 改为该根的局部重绘

### 4.2 渲染：增量更新

候选：

1. 仅合并渲染频率（rAF 内多次触发合并为一次全量重建）——改动最小，但滚动几页后单次全量重建仍涉及数千节点，头像仍会闪，治标不治本
2. 增量更新（选定）：全量重建仅保留给「世界重置」场景，数据到达走局部路径
3. 引入前端框架/虚拟滚动——工程级别过大，违反非目标 1

选 2（我方提议，维护者知悉未反对）。具体语义：

1. 保留一个全量重建入口（现 `render()` 改名或保留为 `renderAll`），仅用于：排序切换、刷新、换视频、首次挂载等整体重置场景
2. 数据到达的局部路径：
   1. 新一页根评论：逐条 append 新元素到 `.btr-list` 末尾，已有元素不动
   2. 回复树更新（自动加载、手动加载更多、树内发回复）：只重建该根的 `.btr-reply-tree` 子树，根评论自身的既有 DOM（头像、正文、元信息）保持不动，以满足验收 7.3 的元素存活要求
   3. 点赞/点踩、回复框开关：只重建受影响的那一条评论所在的最小范围
   4. 状态文案（`.btr-status`「已加载 X/Y」）与「更多评论」按钮态：直接改 textContent/disabled，不触碰列表
3. 实现机制（元素缓存 Map<rootId, element>、脏标记、现有约 20 处 `render()` 调用点各自映射到全量还是局部）留给 builder，验收只看行为：加载期间已渲染 DOM 不被销毁重建

### 4.3 布局密度：结构对齐原生（用户已选定）

候选：

1. 结构对齐原生（选定）：头像左置并排、元信息合行、长文折叠，预计约 100px
2. 只做减法：保持纵向结构仅收紧间距、合并按钮行，预计只能压到 120～130px，仍比原生高约三成
3. 双布局开关（紧凑模式）：两套样式维护成本高，且用户要的是默认就接近原生

选 1（AskUserQuestion 确认）。要点：

1. 评论单元改为「左头像列 + 右内容列」结构，`renderAuthor`/`renderRoot`/`renderReplyNode` 的 HTML 生成随之调整；头像尺寸沿用现状（根 38px、子 30px）
2. 元信息行合并：时间、IP 属地、点赞、点踩、回复在同一行（flex-wrap 兜底窄屏）
3. 根评论的「收起相关回复 / 展开相关回复」入口从独立行移出：展开态放回复树底部（原生「收起」同位置），收起态并入元信息行下方——具体几何留给 builder 以浏览器实测对比原生定
4. 长文折叠：`.btr-message` 用 `-webkit-line-clamp` 实现，行数取 `reply_control.max_line`（缺失默认 6）；渲染后比较 scrollHeight 与 clientHeight 决定是否显示「展开」按钮；每条的展开状态存 JS state（reply id 的 Set），局部/全量重渲染均不丢
5. 间距：`.btr-root` padding 从 20px 收到约 12px，正文/元信息 margin 相应收紧
6. 树形缩进线（`.btr-node-line`）与 `--btr-depth` 缩进适配新布局：线与头像列的几何关系由 builder 浏览器实测决定，层级视觉必须保留

### 4.4 IP 属地

无分歧直接做：

1. `normalizeReply` 增加 `location: reply.reply_control?.location || ""`
2. `renderMeta` 时间之后渲染，样式同元信息行 muted 文本；字段为空不输出该 span
3. 字段值自带「IP属地：」前缀，原样显示不做二次加工

## 5. 决策清单

### 5.1 维护者已拍板（本次对话确认）

1. 默认展示回复的产品行为不变，不做收起设置项
2. 加载改滚动分页：首屏 1 页 + 滚动触底自动加载
3. 渲染改增量更新，消除闪烁
4. 密度按「结构对齐原生」方案做
5. IP 属地实现

### 5.2 我方决定（批准文档时请过目）

1. 截断态禁止 observer 自动触发翻页，「更多评论」按钮作手动重试
2. 长文折叠行数跟随接口 `max_line`，缺失默认 6；折叠展开状态存 JS state
3. IP 属地无独立开关，字段缺失即静默不显示
4. `MAX_AUTO_ROOT_PAGES`、`ROOT_PAGE_INTERVAL_MS` 常量废弃
5. 全量重建仅保留给排序切换/刷新/换视频/首次挂载等整体重置场景
6. 回复树自动拉取行为保留（只为已加载的根评论排队）

## 6. 留给 Builder 的裁量

1. 增量渲染的具体实现：元素缓存结构、脏标记 API、现有约 20 处 `render()` 调用点到全量/局部路径的映射
2. 具体 HTML/CSS 几何：头像列宽、缩进线与头像列的定位关系、展开/收起入口与长文「展开」按钮的样式，以浏览器实测对比原生为准
3. 折叠判定、location 归一化等新增纯逻辑是否抽独立模块做 node:test 单测（参照 theme.js UMD 模式），倾向抽（本次无新增持久化设置项）
4. 既有交互与增量渲染的兼容细节：`submitReply` 发回复成功后应更新对应树并可见新回复；点赞/点踩后局部重绘不丢长文折叠状态
5. IntersectionObserver 生命周期：换视频（SPA 路由）、切原生评论区、排序重置时的挂起与恢复
6. manifest.json 版本号 bump 与 STORE_LISTING.md、README.md 更新

## 7. 验证与验收

1. 单测：`node --test test/`，现有主题测试不回归；新增纯逻辑（location 归一化、折叠判定等，若抽出）有测试覆盖
2. 请求数验收：chrome-devtools MCP 打开真实视频页，Network 面板确认首屏仅 1 页根评论 + 该页回复树请求；滚动触底后才出现下一页
3. 无闪烁验收：加载期间用 devtools 确认已渲染的评论元素不被销毁重建（元素句柄持续存活）；肉眼观察打开视频到稳定全程无连续闪烁
4. 高度验收：同一视频截图对比原生与插件单条高度，单行根评论约 100px（±20%）
5. IP 属地验收：登录态确认显示「IP属地：xx」；退出登录（或无痕窗口）确认静默不显示且无报错
6. 长文折叠验收：找一条超 6 行评论确认折叠与「展开」按钮；展开状态在点赞等局部重绘后保持
7. 回归清单：主题切换、切换原评论区、最热/最新排序、点赞/点踩、发回复、风控截断提示与手动重试、换视频后状态重置、滚动加载在以上场景重置后仍正常
