# 树形评论对齐原生体验设计文档

日期：2026-11-26
状态：待批准
来源：Chrome 商店用户反馈三条——默认显示回复过多、单条评论比原生高、请求增加 IP 属地显示

## 1. 意图与背景

用户反馈原文要点：

1. 默认情况下过多地显示回复，逻辑与原生评论区明显不同
2. 树形评论的单条高度明显高于原生，信息密度不如原生，两者叠加观感不好
3. 推荐添加显示 IP 属地功能

核实结论（均已实测或对照代码确认）：

1. 反馈成立且现状比描述更严重：插件默认自动连翻最多 10 页根评论（最多 200 条），每条有回复的根评论自动再发一次请求拉第一页 20 条回复，且全部展开渲染。极端情况一个视频页背后是 200+ 次接口请求、4000+ 条评论 DOM。这同时是历史上「渲染风暴」「主线程饱和」两次修复的根源
2. 反馈成立：按当前 CSS 计算，一条单行文字的根评论约 163px（`.btr-root` 上下 padding 40 + 头像行 38 + 正文 33 + 元信息行 26 + 「收起相关回复」按钮行 26）。四处结构差异：头像独占一行（原生头像在左与内容并排）、padding 偏大、元信息与操作入口分成两行、长评论不按接口 `max_line` 折叠
3. 可实现：字段为 `reply_control.location`，值形如「IP属地：广东」，仅登录用户下发、仅 2022-07-25 之后的评论存在。插件走页面上下文请求且 `credentials: "include"`，登录用户可直接拿到。B 站网页版原生至今不渲染该字段，插件做了是差异化卖点

用户已拍板两个方向（AskUserQuestion 记录）：

1. 回复显示策略：以「对齐原生」为基线，做成用户设置（默认收起 / 默认展开），localStorage 记住选择
2. 布局密度：结构对齐原生（头像左置并排、收紧间距、元信息合行、长文按 max_line 折叠）

## 2. 目标、非目标、反目标

### 2.1 目标

1. 默认状态（设置为收起时）首屏接口请求降到个位数：根评论 1 页 + 预览回复零请求（预览来自根评论响应的 `replies` 数组，接口白送）
2. 单行评论渲染高度逼近原生，目标约 100px，最终以浏览器实测对比同视频原生评论区为准
3. 登录状态下元信息行显示「IP属地：xx」；未登录、老评论静默不显示，无占位无报错
4. 保留树形缩进与层级线视觉表达（插件核心卖点）
5. 设置项遵循主题按钮既有模式（localStorage + 头部按钮循环切换），切换即时生效不刷新页面

### 2.2 非目标

1. 不重构为增量渲染或虚拟滚动——默认收起后全量 `innerHTML` 重渲染的规模可接受
2. 不做回复树内部的滚动无限加载，树内「加载更多回复」保持点击式
3. 不为 IP 属地提供独立开关
4. 不改动 API 请求通道（页面上下文优先、background 兜底的双通道结构不动）
5. 不引入 WBI 签名（现有通道已验证可用）

### 2.3 反目标（功能做出来也算失败）

1. 默认状态请求数没有下降
2. 树形层级视觉（缩进线）丢失
3. 未登录用户因 `location` 字段缺失看到报错或空占位
4. 风控截断检测（`isRootListTruncated`）在首屏页数减少后开始误报或漏报
5. 发回复、点赞等既有交互在新布局下回归失败

## 3. 约束（实测事实，2026-11-26 验证）

1. `/x/v2/reply/main` 未登录响应的 `reply_control` 无 `location` 键；API 文档（bilibili-API-collect）与多个开源项目（blblcd、BiliReveal）确认该字段需登录，且仅 2022-07-25 11:00 后发布的评论有效
2. `reply_control.max_line` 在根评论响应实测存在（值为 6），原生用其决定长文折叠行数
3. 根评论响应的 `replies` 数组自带 2～3 条预览回复；`seedPreviewReplies`（content.js:602）已实现消费，不产生网络请求
4. 子回复接口 `/x/v2/reply/reply` 与主接口返回同构 Reply 对象（`normalizeReply` 共用，`time_desc` 已在两条链路线上生效）；`max_line`/`location` 缺失时按默认值回退（6 / 不显示），实现时用登录态浏览器抽验
5. curl 高频直连会触发风控（返回 -352 或 HTML 错误页），验证一律走页面上下文或浏览器，不用裸 curl 下结论
6. `render()` 是全量 `innerHTML` 重渲染（content.js:818），展开/折叠等 UI 状态必须存 JS state（Map/Set），不能依赖 DOM 存活
7. 测试基建：`node:test`（test/theme.test.js 为样例），纯逻辑模块用 UMD 模式（module.exports + 全局挂载）便于单测，theme.js 是现成范本
8. 主题设置的持久化模式可直接复用：STORAGE_KEY + try/catch 包裹的 read/write + 头部按钮 data-action 切换（theme.js:92-106）

## 4. 方案与取舍

### 4.1 默认回复显示策略

候选：

1. 完全对齐原生：默认只显示 2～3 条预览，点击展开才请求全树；根评论首屏自动翻页从 10 页降到 1 页
2. 自动加载但默认收起：仍自动拉每条根评论的第一页回复，UI 收起
3. 以方案 1 为基线 + 用户设置项（默认收起 / 默认展开）

选 3（用户拍板）。理由：方案 1 直接解决反馈与请求风暴；方案 2 不解决请求问题；设置项照顾习惯「打开即见全树」的老用户。

具体语义：

1. 新增设置 `defaultExpand`，默认值 false（收起、原生式）。理由：反馈抱怨的正是默认显示过多，新用户应先看到原生式体验；老用户可一键切回
2. 设置入口：头部按钮区新增一个按钮，与「主题：自动」同款式同交互（点击两态切换），文案「回复：默认收起」/「回复：默认展开」，localStorage 持久化
3. 收起模式行为：
   1. 根评论首屏只加载 1 页（约 20 条），后续翻页由「更多评论」按钮或滚动触底自动触发
   2. 每条根评论只播种预览回复（`seedPreviewReplies`，零网络请求），预览下方显示「展开 X 条回复」入口（原生式）
   3. 点击展开走现有 `loadReplies` 分页；再点收起回到只显示预览节点，已加载数据保留在 store 不重复请求
4. 展开模式行为：维持现状（每条有回复的根评论自动拉第一页 20 条回复并展开）。根评论首屏页数与滚动加载策略两种模式一致（固定 1 页 + 滚动触底），设置只控制回复树，避免双模式组合语义
5. 滚动自动加载：IntersectionObserver 观察 `.btr-footer`，可见且非忙、未结束、未截断时触发加载下一页根评论；「更多评论」按钮保留，兼作风控截断时的手动重试入口。理由：首屏降到 1 页后没有滚动加载会造成明显倒退；截断态禁止自动触发，避免重试风暴
6. `loadRootComments` 改为每次调用加载 1 页（现循环上限 `MAX_AUTO_ROOT_PAGES = 10` 的语义废弃），风控截断检测逻辑不变但需在 1 页样本下回归验证

### 4.2 布局密度（结构对齐原生）

候选：

1. 结构对齐原生：头像移左侧与内容并排、收紧 padding、元信息与操作按钮合行、长文按 max_line 折叠
2. 只做减法：保持纵向布局，仅收紧间距、合并按钮行
3. 加紧凑模式开关，两套布局并存

选 1（用户拍板）。理由：头像独占一行是最大结构性高度差，方案 2 预计只能压到约 130px；方案 3 双套样式维护成本高。

要点：

1. 评论单元改为「左头像列 + 右内容列」结构，`renderAuthor`/`renderRoot`/`renderReplyNode` 的 HTML 生成随之调整；头像尺寸沿用现状（根 38px、子 30px）
2. 元信息行合并：时间、IP 属地、点赞、点踩、回复在同一行（flex-wrap 兜底窄屏）；「展开/收起 X 条回复」不并入元信息行，作为预览区下方的独立入口（原生同位置）
3. 长文折叠：`.btr-message` 用 `-webkit-line-clamp` 实现，行数取 `reply_control.max_line`（缺失默认 6）；渲染后比较 scrollHeight 与 clientHeight 决定是否显示「展开」按钮；每条的展开状态存 state（reply id 的 Set），全量重渲染不丢
4. 树形缩进线（`.btr-node-line`）适配新布局：线与头像列的几何关系由 builder 浏览器实测决定，层级视觉必须保留
5. 间距目标：根评论 padding 从 20px 收到约 12px，正文/元信息 margin 相应收紧，单行根评论总高（含间距）约 100px

### 4.3 IP 属地

无分歧直接做：

1. `normalizeReply` 增加 `location: reply.reply_control?.location || ""`
2. `renderMeta` 时间之后渲染，样式同 meta 行 muted 文本；字段为空不输出该 span
3. 字段值自带「IP属地：」前缀，原样显示不做二次加工

## 5. 决策清单

### 5.1 用户已拍板

1. 回复策略：对齐原生基线 + 用户设置项（默认收起 / 默认展开）
2. 布局：结构对齐原生（头像并排 + 收紧 + 合行 + 长文折叠）
3. IP 属地：实现

### 5.2 我方决定（批准文档时请过目）

1. 设置默认值为收起（原生式），老用户更新后行为变化可用设置一键还原
2. 根评论首屏固定 1 页、两种模式一致，新增滚动触底自动翻页
3. 长文折叠行数跟随接口 `max_line`，缺失默认 6
4. IP 属地无开关，字段缺失即不显示
5. 设置按钮文案「回复：默认收起 / 回复：默认展开」，与主题按钮同款交互
6. `loadRootComments` 语义改为每次 1 页，`MAX_AUTO_ROOT_PAGES` 废弃

## 6. 留给 Builder 的裁量

1. 具体 HTML/CSS 几何：头像列宽、缩进线定位、展开入口（chip）样式，以浏览器实测对比原生为准
2. 设置读写与折叠状态是否抽独立纯逻辑模块做 node:test 单测（参照 theme.js UMD 模式），倾向抽
3. store 数据结构如何标记预览节点（previewIds Set 或等价机制），需满足「收起时只渲染预览、展开渲染全部、数据不重复请求」
4. 既有交互与新状态的兼容处理：`submitReply` 发回复成功后应自动展开对应树并可见新回复；排序切换（`resetRootComments`）后设置保持；点赞/点踩重渲染不丢折叠状态
5. manifest.json 版本号 bump 与 STORE_LISTING.md、README.md 更新
6. 滚动加载的 observer 生命周期（换视频、切原生评论区时的挂起与恢复）

## 7. 验证与验收

1. 单测：`node --test test/`，现有主题测试不回归，新抽纯逻辑（设置读写、折叠判定、location 归一化）有测试覆盖
2. 请求数验收：chrome-devtools MCP 打开真实视频页，默认收起状态下 Network 面板确认根评论 1 页、无自动回复请求；切默认展开后恢复自动拉第一页
3. 高度验收：同一视频截图对比原生与插件单条高度，单行评论总高约 100px（±20%）
4. IP 属地验收：登录态确认显示「IP属地：xx」；退出登录（或无痕）确认静默不显示且无报错
5. 回归清单：主题切换、切换原评论区、最热/最新排序、点赞/点踩、发回复、风控截断提示、换视频（SPA 路由）后状态重置
6. 长文折叠验收：找一条超 6 行评论确认折叠与「展开」按钮，展开状态在点赞等重渲染后保持

## 8. 关键文件

1. src/content.js：加载策略（loadRootComments、autoLoadReplyPages、runAutoReplyQueue、seedPreviewReplies）、渲染（renderRoot、renderReplyNode、renderAuthor、renderMeta）、设置按钮接线
2. src/styles.css：布局重构、密度、折叠样式、缩进线
3. src/theme.js：设置持久化模式范本（不改其逻辑）
4. test/theme.test.js：测试样式范本
5. manifest.json：版本号
